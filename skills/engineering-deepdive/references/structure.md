# 问题驱动 + 总→分→合：结构详解

SKILL.md 给了五个核心模式的概览。这份 reference 把其中两个最影响篇章组织的模式 —— 问题驱动 + 总分合 —— 展开讲。

## 一、为什么"问题驱动"比"功能列表"更好读

LLM 默认会把技术内容组织成<strong>功能列表</strong>："这个东西有 N 个功能，分别介绍。" 这种组织的根本问题是：

1. **读者的注意力没有锚** —— 翻到第 3 个功能时已经忘了第 1 个，因为各功能之间没有逻辑联系
2. **读者不知道为什么这些功能存在** —— "功能"是结果，不是动机
3. **细节平等** —— 每个功能在结构上同等重要，但实际工程里它们重要性差很多倍

**问题驱动**反过来：把读者真的会问的问题放到章节标题。读者每读一节，<strong>都在解决他自己脑子里的一个 query</strong>。这两件事的差异在长文里指数放大 —— 一篇 5000 字的功能列表读完读者记得 20%；一篇 5000 字的问题串读完读者能复述出主线。

## 二、怎么挑核心问题

好问题三个特征：

1. **读者真的会问** —— 不是 "X 是什么"，而是 "为什么 X 不是更简单的 Y"
2. **官方文档不答** —— 官方 README / API doc 已经回答的问题，写出来没价值
3. **能引出一个非平凡的设计决策** —— 答案是 "因为我们做了 trade-off"，而不是 "因为这是规范"

怎么挑？两条路径：

### 路径 A：从"代价"反推

读代码时找到一段"看起来过度工程化"的逻辑（用了不寻常的数据结构、加了一层间接、用了不对称的策略）—— 这通常对应一个非平凡决策。问 "为什么不简单地 X？" 就是好问题。

例：
- 发现 MemoryStore 写盘用了 tempfile + os.replace 而不是直接 `open("w")` → "为什么不直接 open + flock？"
- 发现 prefetch_all 调用在 tool loop 之外 → "为什么不在 loop 内每次调？"

### 路径 B：从"边界"反推

读到 N 个看起来矛盾的需求被同时满足（写盘要安全 + reader 不需要锁 + 跨平台），这通常对应一个非平凡设计。问 "怎么同时满足 X 和 Y？" 就是好问题。

## 三、问题之间的 narrative flow

10 个孤立的问题不如 10 个串起来的问题。好的问题串有一个隐藏的<strong>故事线</strong>，每个问题的答案自然引出下一个问题：

```
Q1: 一个跑一年的 agent 记忆该怎么设计？
    答案：两条通道
    ↓ 引出
Q2: 那"总有效"的通道怎么注入又不烧 prefix cache？
    答案：Frozen snapshot
    ↓ 引出
Q3: 反过来，"按需召回"通道怎么不破坏 cache？
    答案：注入 user message
    ↓ 引出
Q4: 模型把内部围栏复读出去怎么办？
    答案：流式 scrubber 状态机
    ↓ ……
```

每个 ↓ 都是<strong>读者会自然产生的下一个疑问</strong>。如果读完一个问题，读者不会自然问下一个，说明排序有问题。

## 四、总→分→合 的三段长度

| 段 | 篇幅占比 | 目标 |
|----|---------|------|
| **总** | 10-15% | 一句话讲完整套设计 + 总览图 + 接下来要展开的问题列表 |
| **分** | 70-80% | 每个核心问题一节 |
| **合** | 10-15% | 数据流整合图 + 一句话总结 + 设计哲学反射 |

### 总的写法

总只做三件事：

1. **一句话讲完整套设计**：不是 "这个系统包含 ABCD"，而是 "这套设计本质上是在解决 X 问题，办法是 Y"
2. **一张总览图**：物理布局 / 数据流 / 模块关系（三选一，不要三个都画）
3. **接下来要回答的问题列表**：让读者知道这篇文章会带他去哪里

例：

> Hermes 的 memory 子系统一句话讲完：<strong>"总是有效的核心事实"和"按需召回的语义记忆"分进两条物理通道</strong>—— 前者用 system prompt 锁 prefix cache，后者用 user message 走围栏注入。整个设计的复杂度都源于"总是有效"和"按需"这两个词分别要解决的工程问题。

### 分的写法

每节大致 200-500 字 + 0-1 张图。如果一节超过 800 字，考虑拆成两个问题。

每节内部模板：

1. **问题描述**（1-2 句）：问题是什么、为什么非平凡
2. **朴素方案** 卡片（1-3 个）：每个 1-2 句话讲为什么不够
3. **真实方案** 卡片：1-3 句话讲 Hermes 的选择
4. **机制展开**（如有必要）：代码片段 / 配图 / 短表
5. **核心亮点** callout：1 句工程主张 + 1 句推广到哪些场景

### 合的写法

合不是"再总结一遍每节讲了什么"（那是 AI 默认会做的事，也是<strong>最浪费篇幅</strong>的事）。合做两件:

1. **一图整合**：把所有问题的答案画在<strong>同一张数据流图</strong>上。比如把 10 个问题的答案画成一张 swimlane 时序图，T1 → T10，对应回各个 Q。
2. **抽象到模式层**：3-5 条<strong>能从这套设计推广出去的工程主张</strong>。"不变性优先"、"协议演进的优雅降级"、"persistence ≠ visibility" —— 这些都是<strong>能用在其他系统里的思维工具</strong>。

合的部分写好的标志是：读者读完<strong>不仅理解了这个系统，还学到了一种思考方式</strong>。

## 五、几个常见的结构反模式（避免）

### 反模式 1：教科书序

"第一章 历史 / 第二章 基础概念 / 第三章 核心算法 / 第四章 实现细节"

技术 essay 不是教材。读者不需要从头按部就班学，他需要直接跳到他关心的问题。

### 反模式 2：流水账

按代码文件顺序讲："`memory_provider.py` 定义了 ABC，`memory_manager.py` 实现了编排，`memory_tool.py` 是工具入口……"

这是文件清单，不是 essay。读者不关心你按什么文件组织，他关心系统在做什么。

### 反模式 3："优势-劣势-总结"对仗

"该方案的优势在于 A、B、C；不足之处包括 D、E、F；综上所述……"

这是大学论文格式，不是工程写作。工程写作里 trade-off 是<strong>嵌入在叙事里</strong>的：写到方案细节时顺便提一句"代价是 D，我们接受这个 D 因为 X"。不要单独开一节列优劣。

### 反模式 4：前后呼应过度

每节末尾"这一节我们讨论了 X，下一节将讨论 Y"。

LLM 默认有这种习惯，要主动删掉。读者翻页就能看到下一节标题，不需要你预告。

## 六、检验自己的结构

写完后，问自己三个问题：

1. **能不能只看每节标题就讲出文章主线？** 如果不行，标题不够强或顺序有问题。
2. **每节里"为什么"和"是什么"哪个先出现？** 如果"是什么"先出现，结构有问题 —— 改成先问问题。
3. **去掉"合"那一节，文章还剩什么？** 如果剩下的还能读完，说明合写得没用 —— 重写。
